# Backlog

What is not yet planned into a phase. Two lists, discussed separately:

- **Ideas** — something the app does not do yet: a new page, a new capability.
- **Improvements and fixes** — something that exists and works wrongly, slowly or
  awkwardly.

A deferral or a new idea found while working a phase goes here, not into the phase
doc. Planning a phase marks the items it takes `planned (phase N)`. A row that is done
or no longer applies moves to [`backlog-archive.md`](backlog-archive.md) with its
outcome, so this file holds only live work.

## Ideas

| Item | Status | From | Notes |
| --- | --- | --- | --- |
| **`/profile` page** | open | phase 2 | A `SoonPage` placeholder today. Needs a candidate-profile store; the master resumes would live there (see the next row). |
| **Tailor a resume from the vacancy page** | open | phase 3.1 | A button on the vacancy runs what the `resume-ats-tailor` skill does today, inside the app. The posting text is already in JSC (`fullText`); the master resumes are not — they live on the user's disk and would move into `/profile` first. |
| **A UI for the status journal, and comment CRUD** | open | phase 3.1 | A separate page. The `StatusChange` journal and the `Comment` table exist; nothing shows the journal, and comments can only be appended. |
| **Auth and an HTTP MCP transport** | open | phase 3, 2026-09-29 | MCP is stdio-only and the API has no auth. Nothing may be exposed to the cloud before this lands. The web wanted (2026-09-29): a login page first; sign in with Google, LinkedIn (a job app — the preferred one) or email + password; an existing Google session signs in by itself (Google One Tap / FedCM). How LinkedIn's sign-in looks is still to research. |
| **Vacancy intake via n8n, scored later on the subscription** | open | 2026-09-29, 2026-10-01 | n8n workflows pull vacancies from job sites, with a directory of sources in n8n; the app's settings choose which sources are on. They write each vacancy, posting text included, straight into JSC over REST, **unscored**. A first screening drops the invalid and irrelevant ones, the user keeps the relevant ones, then a Claude Desktop session pulls the unscored ones over MCP and sends back only `matchScore`, `recommendation` and the review. Triage statuses follow as today. Two goals. First, the agent never sends a posting's text back: today `save_vacancy` takes `fullText` as tool input, so the text passes through the agent twice. Second, scoring runs on the Claude subscription, not on a paid API key, so the LLM step cannot live in n8n. To think through together before a phase doc: where the first screening runs (n8n rules, or the user in the web); what an unscored row holds in `matchScore` / `recommendation`, and how `/stats`, the `recommended` sort and the tables treat it; analyze-once (invariant 2) when an analysis is attached to an existing row, since today an existing `applyUrl` drops the analysis, so this needs a new MCP tool; dedup against the vacancy log; n8n local (Docker) or in the cloud, where the auth row must land first; which skills change (`vacancy-evaluator`, `vacancy-discovery`). |
| **Recent activity: every status move, and a full table** | open | 2026-10-01 | The dashboard's Recent activity shows the 6 latest **pipeline** moves only: `StatsService` filters `recent` to `PIPELINE_STATUSES`. Wanted: every status move, wherever it came from (triage on the vacancy pages, statuses the agent sets from email, and so on). Each of these already writes a `StatusChange` row, but the journal does not record its source. Then a bigger activity table: the latest 100 moves, scrolling, with a status filter like the other tables have. That needs its own query (`/stats` carries 6). This overlaps the status-journal UI row above; the table may be that UI. |
| **Filters per column, in a modal** | open | 2026-10-01 | Not for now. A Filter button opens a modal with one rule per column: a range for the date and the score; checkboxes over every value for the recommendation and the status; "contains" for company, title and comments. `/applications` gets the same, plus sorting and filtering by CV (tailored or not). Salary: maybe "contains / does not contain" later. Per-column sorting comes with it: today a table sorts only by the `sort` query (`newest` / `recommended`). The REST list queries take a single `recommendation` and no ranges, so the API grows with it. |
| **Live updates over WebSocket** | open | 2026-09-29 | Statuses will change without the user: an n8n flow reads a reply email and sets the status at once. The server pushes the change, the web updates without a reload. Until then, phase 4.2 step 5 refetches the company modal on every open. |
| **Turborepo / Nx** | open | phase 3.1 | npm workspaces is enough for four packages. Wanted for learning, in its own phase; would also answer the `core` dev-loop row below. |
